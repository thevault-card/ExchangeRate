## 0. 개요

카드 시세(현재 USD 기준)를 앱에서 원화(₩)로 보여주고, 마이페이지에서 내 자산 가치를 S&P500·코스피와 비교해서 보여주기 위한 **기준 데이터 수집 파이프라인 2개**입니다.

| 파이프라인 | 수집 대상 | 데이터 소스 | 목적 |
|---|---|---|---|
| ① 환율 | USD → KRW 매매기준율 | 한국수출입은행 Open API | 카드 시세 원화 환산 |
| ② 시장지수 | S&P500 종가 | yfinance (Yahoo Finance) | 자산 가치 비교 차트 |
| ② 시장지수 | 코스피 종가 | 공공데이터포털 (금융위원회) | 자산 가치 비교 차트 |

**모두 카드/시세 수집 파이프라인과 완전히 분리된 독립 배치**입니다. 서로의 실행을 기다리거나 의존하지 않습니다.

## 1. 환율 파이프라인

### 1-1. 데이터 소스 — 한국수출입은행 Open API

```
GET https://oapi.koreaexim.go.kr/site/program/financial/exchangeJSON
    ?authkey={발급받은 인증키}
    &searchdate={YYYYMMDD}
    &data=AP01
```

- **주소 재확인 완료 (2026-08-02)**: 위 URL이 현행 정본입니다.
- 🔴 **구 도메인은 이미 종료됐습니다.** `www.koreaexim.go.kr`은 2025-06-25 변경 공지 후 **2026-04-30부로 서비스 종료**됐습니다. 인터넷의 블로그 예제 코드는 대부분 구 도메인이라 **그대로 복붙하면 동작하지 않습니다.**
- **인증키 발급**: [공공데이터포털 — 한국수출입은행 환율 정보](https://www.data.go.kr/data/3068846/openapi.do) 또는 수출입은행 Open API 사이트에서 무료 발급 (본인인증 필요)
- **트래픽 제한**: 포털에 명시된 고정 한도는 없고 "기관 정책에 따라 상이"입니다. 하루 2~3회 호출이라 문제되지 않지만, **초기 백필을 돌린다면 사전 확인이 필요합니다** (단, R-4 결정으로 백필 필요성 자체가 사라짐 — [§3-1](#3-1-원화-환산--현재-환율-기준) 참조)
- `searchdate`는 조회하려는 날짜. 응답은 그 날짜에 실제 고시된 환율이며, **주말·공휴일로 조회하면 빈 배열**이 옵니다 (고시 자체가 없음)

### 1-2. 응답 예시 및 파싱 주의사항

```json
[
  { "result": 1, "cur_unit": "USD", "cur_nm": "미국 달러", "deal_bas_r": "1,385.20", "ttb": "...", "tts": "..." }
]
```

**⚠️ 구현 시 반드시 처리해야 할 함정 3개**

| 함정 | 내용 | 처리 |
|---|---|---|
| ① 콤마 포함 문자열 | `deal_bas_r`이 `"1,385.20"`처럼 **문자열에 콤마 포함** | 콤마 제거 후 파싱. `Decimal(s.replace(",", ""))` — **`float()` 대신 `Decimal` 사용**(금액 정밀도) |
| ② **빈 배열 ≠ 항상 정상** | 인증키 오류·한도 초과 때도 **HTTP 200 + 빈 배열**이 옵니다 | 반드시 `result` 코드 검사: **1=성공 / 2=데이터코드 오류 / 3=인증코드 오류 / 4=일일제한 초과.** 1이 아니면 **실패로 처리하고 알림** ([§4-2](#4-2-실패-감지와-알림)) |
| ③ 통화 필터링 | 응답 배열엔 USD 외 40여 개 통화가 섞여 옴 | `cur_unit == "USD"`인 항목만 사용 |

- 우리가 쓸 필드는 **`deal_bas_r`(매매기준율)만**. `ttb`(송금받을때)/`tts`(송금보낼때)는 사용하지 않음 — 표시용 기준 환율이 목적이라 매매기준율이 맞음
- ~~JPY 100엔 기준 함정~~ → **v1 범위 제외**([부록 A](#부록-a-향후-계획--jpy-엔화-수집))

### 1-3. 수집 스케줄

- **영업일 1일 2회**, KST **11:10** (고시 직후) + **16:10** (재확인·갱신분 반영)
- 근거: 수출입은행 매매기준율은 통상 **오전 11시경 최초 고시**됩니다. 그 이전 조회는 빈 응답 또는 전일 값일 수 있습니다.
- 16:10 재확인분은 값이 동일하면 **UPDATE하지 않습니다**([§1-5](#1-5-upsert-규칙))
- 주말·공휴일: 배치를 돌리지 않거나, 돌려도 빈 응답이 정상 → **저장 행 없음.** 화면 표시는 carry-forward로 처리([§3-2](#3-2-휴일주말-처리--carry-forward))

### 1-4. 대상 테이블 — `silver.fx_exchange_rates`

| 컬럼명 | 타입 | Key | 설명 |
|---|---|---|---|
| currency_code | VARCHAR(10) | PK(1) | `USD` 고정 (v1). PK 첫 번째 순서인 이유는 아래 참고 |
| rate_date | DATE | PK(2) | 조회한 `searchdate` (KST 기준 날짜) |
| base_rate | NUMERIC(12,4) | NOT NULL | `deal_bas_r` 파싱값. `CHECK (base_rate > 0)` |
| source | VARCHAR(30) | NOT NULL | 고정값 `koreaexim` |
| created_at | TIMESTAMPTZ | NOT NULL | 생성일시 (최초 적재) |
| updated_at | TIMESTAMPTZ | NOT NULL | 수정일시 (마지막 갱신) |
| created_batch_id | TEXT | | 생성배치ID (최초 적재한 배치) |
| updated_batch_id | TEXT | | 수정배치ID (마지막 갱신한 배치) |

> **PK 컬럼 순서 주의**: `(currency_code, rate_date)` 순서입니다. 실제 조회가 `WHERE currency_code='USD' ORDER BY rate_date DESC`라 이 순서여야 인덱스를 제대로 탑니다. 순서를 뒤집으면 풀스캔이 됩니다.

> 거버넌스 컬럼 4종(`created_at`/`updated_at`/`created_batch_id`/`updated_batch_id`)은 기존 `ppt_*` 테이블들과 동일한 패턴입니다. → **[미결 D-4] 해당 테이블의 DDL 링크 필요**

> bronze(원본 JSON 보존) 단계는 생략합니다. 하루 1건(USD)뿐인 소량 데이터이고, 같은 날짜로 재조회가 가능합니다.

### 1-5. UPSERT 규칙

배치는 **몇 번 돌려도 결과가 같아야 합니다**(멱등성). 같은 날 두 번 실행해도 PK 충돌로 죽으면 안 됩니다.

```sql
INSERT INTO silver.fx_exchange_rates
       (currency_code, rate_date, base_rate, source, created_at, updated_at, created_batch_id, updated_batch_id)
VALUES ('USD', :rate_date, :base_rate, 'koreaexim', now(), now(), :batch_id, :batch_id)
ON CONFLICT (currency_code, rate_date) DO UPDATE
   SET base_rate        = EXCLUDED.base_rate,
       updated_at       = now(),
       updated_batch_id = EXCLUDED.updated_batch_id
 WHERE silver.fx_exchange_rates.base_rate IS DISTINCT FROM EXCLUDED.base_rate;
```

- 마지막 `WHERE` 절이 핵심입니다. **값이 그대로면 UPDATE를 건너뜁니다** → `updated_at`이 매일 무의미하게 갱신되는 걸 막아, "실제로 값이 바뀐 날"을 나중에 추적할 수 있습니다.

## 2. 시장지수 파이프라인

지수는 **소스가 둘로 나뉩니다.** 하나의 배치 안에서 어댑터 2개를 호출하되, 한쪽이 실패해도 다른 쪽은 저장되도록 **독립적으로 처리**합니다.

### 2-1. S&P500 — yfinance 라이브러리

```python
import yfinance as yf

df = yf.download("^GSPC", period="5d", interval="1d", auto_adjust=False)
# df.index = 거래일(미국 동부 기준 날짜), df["Close"] = 종가
```

- **인증키 불필요, 설치만 하면 됨** (`uv add yfinance`)
- `period="5d"`로 최근 5거래일을 매번 받아 UPSERT → **배치가 하루 실패해도 공백이 안 생깁니다**

> 🔴 **상용 서비스 전환 시 반드시 재검토할 것**
>
> yfinance는 **Yahoo Finance의 비공식(내부) 엔드포인트를 스크래핑**하는 라이브러리입니다. 라이브러리 자체는 오픈소스지만 **데이터 이용권은 별개**입니다.
>
> - **약관 리스크**: Yahoo 약관상 상업적 재배포가 허용되지 않습니다. 실서비스 출시 전 법무 확인 필요.
> - **안정성 리스크**: 예고 없이 스펙 변경·차단될 수 있습니다(과거 crumb/cookie 인증 추가 전례 있음). SLA가 없습니다.
> - **대응**: 개발·검증 단계에서는 yfinance로 진행하되, **상용 출시 시점에 유료 데이터 API로 교체**하는 것을 전제로 설계합니다.
> - **교체 후보**: Polygon.io · Twelve Data · Alpha Vantage · Nasdaq Data Link · LSEG(Refinitiv)
> - **설계 요구사항**: 소스 교체가 쉽도록 **어댑터 인터페이스 뒤에 숨깁니다.** 데이터를 가져오는 함수 시그니처(`fetch_index(code, from, to) -> list[IndexPoint]`)를 먼저 정하고, yfinance 구현체는 그 뒤에 둡니다. `market_indices.source` 컬럼에 어느 소스에서 왔는지 기록해 교체 시점 전후를 구분할 수 있게 합니다.

### 2-2. 코스피 — 공공데이터포털 (금융위원회_지수시세정보)

```
GET https://apis.data.go.kr/1160100/service/GetMarketIndexInfoService/getStockMarketIndex
    ?serviceKey={인증키}
    &resultType=json
    &basDt={YYYYMMDD}
    &idxNm=코스피
```

- **데이터 출처**: 한국거래소(KRX) → 금융위원회 → 공공데이터포털. **공식 데이터**라 yfinance와 달리 약관 리스크가 없습니다.
- **인증키**: [공공데이터포털](https://www.data.go.kr/tcs/dss/selectApiDataDetailView.do?publicDataPk=15094807)에서 활용신청 (무료, 자동승인)
- **트래픽**: 개발계정 10,000건/일 · 운영계정은 활용사례 등록 시 증액 신청 가능

**⚠️ 공공데이터포털 공통 함정 3개**

| 함정 | 내용 | 처리 |
|---|---|---|
| ① **serviceKey 이중 인코딩** | 포털이 **Encoding 키와 Decoding 키 두 벌**을 발급합니다. `requests`에 `params=`로 Encoding 키를 넘기면 `%`가 다시 인코딩돼 **인증 실패**(`SERVICE_KEY_IS_NOT_REGISTERED_ERROR`)합니다 | **Decoding 키**를 `params=`에 넘기거나, Encoding 키를 URL 문자열에 직접 붙여 보냅니다 |
| ② **한글 파라미터** | `idxNm=코스피`가 한글입니다 | UTF-8 URL 인코딩 확인. 응답에 코스피200·코스닥 등이 섞여 오므로 **`idxNm`이 정확히 `"코스피"`인 항목만** 필터링 |
| ③ **에러도 HTTP 200** | 실패 시에도 200으로 응답합니다 | `response.header.resultCode == "00"`을 검사. 아니면 실패 처리 + 알림 |

> ⚠️ **필드명 검증 필요**: 아래 응답 필드명은 금융위원회 시세정보 API 계열의 공통 규칙을 근거로 한 것으로, **실제 호출로 검증되지 않았습니다.** 구현 착수 시 포털의 "활용가이드" PDF를 받아 대조하세요.
>
> | 필드 | 의미 |
> |---|---|
> | `basDt` | 기준일자 (YYYYMMDD) |
> | `idxNm` | 지수명 |
> | `clpr` | **종가** ← 우리가 쓸 값 |
> | `mkp` / `hipr` / `lopr` | 시가 / 고가 / 저가 |
> | `vs` / `fltRt` | 전일대비 / 등락률 |
>
> 응답 경로: `response.body.items.item[]`

### 2-3. 🔴 수집 스케줄 — 여기에 제약이 있습니다

**지시사항 "장 종료되는 대로 가능한 빨리"를 적용한 결과:**

| 대상 | 원천 확정 시각 (KST) | 데이터 이용 가능 시각 (KST) | 배치 실행 | 마감→반영 지연 |
|---|---|---|---|---|
| 환율 | 11:00경 고시 | 즉시 | **11:10** (+16:10 재확인) | ~10분 ✅ |
| S&P500 | 익일 06:00경 마감<br>(16:00 ET) | 즉시 | **익일 06:30** | ~30분 ✅ |
| 코스피 | 15:30 마감 | 🔴 **익일 13:00 이후** | **익일 13:10** | 🔴 **약 21시간 30분** |

> 🔴 **코스피만 "가능한 빨리"가 구조적으로 불가능합니다.**
>
> 공공데이터포털 금융위원회 지수시세정보는 **실시간이 아니며, "기준일자 다음 영업일 오후 1시 이후" 갱신**됩니다. (금요일 데이터는 다음 주 월요일 제공)
>
> 즉 **월요일 코스피 종가를 화요일 13시가 지나야 받을 수 있습니다.** 앱에서 "오늘 코스피"를 보여줄 수 없다는 뜻입니다.
>
> → **[미결 D-1] 결정 필요.** 아래 3가지 안 중 선택해 주세요.
>
> | 안 | 내용 | 장 | 단 |
> |---|---|---|---|
> | **A. 지연 수용** | 공공데이터포털만 사용, T+1 13:10 실행 | 단순·공식 데이터 | 차트가 항상 하루 늦음 |
> | **B. 소스 교체** | [KRX Data Marketplace OPEN API](https://openapi.krx.co.kr/) 로 변경 | 거래소 직접 제공 | 갱신 시각·요금 미확인(확인 필요) |
> | **C. 2단계 수집** ⭐추천 | 15:40에 yfinance `^KS11`로 **잠정값** 적재 → 익일 13:10 공공데이터포털 **확정값**으로 덮어쓰기 | 당일 표시 + 공식 확정값 둘 다 확보 | 구현 복잡도 증가, `is_provisional` 컬럼 필요 |
>
> **C안을 추천하는 이유**: 사용자에게는 "장 마감 직후 반영"이 보이면서, 저장되는 최종값은 공식 데이터입니다. 지시사항 2번(공공데이터포털)과 5번(가능한 빨리)을 둘 다 만족하는 유일한 안입니다.

### 2-4. 대상 테이블 — `silver.market_indices`

| 컬럼명 | 타입 | Key | 설명 |
|---|---|---|---|
| index_code | VARCHAR(10) | PK(1) | `SPX`(S&P500) / `KOSPI` |
| trade_date | DATE | PK(2) | **해당 거래소의 현지 거래일**. 아래 주의 참조 |
| close_value | NUMERIC(14,2) | NOT NULL | 종가. `CHECK (close_value > 0)` |
| source | VARCHAR(30) | NOT NULL | `yfinance` / `data_go_kr` — 소스 교체 이력 추적용 |
| created_at | TIMESTAMPTZ | NOT NULL | 생성일시 (최초 적재) |
| updated_at | TIMESTAMPTZ | NOT NULL | 수정일시 (마지막 갱신) |
| created_batch_id | TEXT | | 생성배치ID |
| updated_batch_id | TEXT | | 수정배치ID |
| *is_provisional* | *BOOLEAN* | | *[D-1에서 C안 채택 시에만 추가]* 잠정값 여부. 확정값으로 덮어쓸 때 `false` |

> ⚠️ **`trade_date`는 KST로 변환하지 마세요.** 각 지수의 **거래소 현지 날짜**를 그대로 씁니다.
> - 코스피: 공공데이터포털 `basDt`를 그대로 사용 (이미 KST 기준)
> - S&P500: yfinance가 돌려주는 `df.index` 날짜를 그대로 사용 (이미 미국 동부 기준 거래일)
>
> 이유: "S&P500의 8월 1일 종가"는 미국의 8월 1일 종가여야 의미가 맞습니다. KST로 억지 변환하면 서머타임·조기폐장에서 하루씩 어긋납니다. 두 소스 모두 이미 현지 거래일을 주므로 **변환하지 않는 것이 곧 정답**입니다.

> ⚠️ **`close`가 `null`인 인덱스는 건너뜁니다.** yfinance는 휴장일·장중 미확정 구간에서 `NaN`을 반환합니다. 그대로 UPSERT하면 **이미 들어간 확정 종가를 `null`로 덮어씁니다.**

UPSERT 규칙은 환율과 동일합니다 (`ON CONFLICT (index_code, trade_date) DO UPDATE ... WHERE close_value IS DISTINCT FROM ...`).

> bronze 단계는 생략. 지수 값 자체가 단순 숫자라 재처리 필요성이 낮습니다.

## 3. 소비 규칙 (gold 레이어)

silver 테이블에는 **실제로 발표된 값만** 저장합니다. 빈 날짜를 메우거나 환율을 곱하는 것은 **모두 gold 뷰에서** 합니다. (silver = 사실, gold = 표현)

### 3-1. 원화 환산 — 현재 환율 기준

**결정(R-4): 과거 시세든 오늘 시세든, 원화 환산에는 언제나 "가장 최신 환율" 하나만 씁니다.**

```sql
CREATE OR REPLACE VIEW gold.v_card_price_krw AS
WITH latest_fx AS (
  SELECT base_rate, rate_date
    FROM silver.fx_exchange_rates
   WHERE currency_code = 'USD'
   ORDER BY rate_date DESC
   LIMIT 1
)
SELECT p.*,
       ROUND(p.market_price * f.base_rate)  AS market_price_krw,
       f.base_rate                          AS applied_fx_rate,
       f.rate_date                          AS applied_fx_date
  FROM silver.fact_card_price p
  LEFT JOIN latest_fx f ON true;
```

- ⚠️ **`LEFT JOIN ... ON true`이지 `CROSS JOIN`이 아닙니다.** `CROSS JOIN`으로 쓰면 환율 테이블이 비었을 때 **시세 행이 통째로 사라집니다**(0건 응답). LEFT JOIN이면 원화만 NULL이고 USD 시세는 정상 노출됩니다.
- `applied_fx_rate` / `applied_fx_date`를 **반드시 함께 내려보냅니다.** 앱이 "₩1,385.20 기준 (8/1 고시)"를 표기해야 하기 때문입니다.
- KRW는 정수 원 단위 반올림(`ROUND()`).

**이 결정의 결과 — 알고 있어야 할 3가지**

1. ✅ **과거 환율 백필이 불필요합니다.** 최신 환율 1건만 있으면 전 기간이 환산되므로, 파이프라인을 오늘 켜도 과거 시세가 즉시 원화로 보입니다.
2. ✅ **자산 수익률에서 환율 효과가 제거됩니다.** 전 구간에 같은 환율을 곱하므로 원화 곡선의 모양이 USD 곡선과 동일합니다. → S&P500(USD 기준)과 비교할 때 **환율 착시가 사라져 비교가 공정해집니다.**
3. ⚠️ **과거 가격 표시가 매일 바뀝니다.** 환율이 오르면 "3개월 전 가격"도 같이 올라갑니다. 사용자가 "어제 본 숫자와 다른데?"라고 느낄 수 있으므로 **`applied_fx_date` 표기가 선택이 아니라 필수**입니다.

`fx_exchange_rates`의 과거 이력은 환산에 쓰이진 않지만 **감사·표기·향후 정책 변경 대비로 계속 쌓습니다.**

### 3-2. 휴일·주말 처리 — carry-forward

**결정(R-3): 값이 없는 날은 직전 최신값으로 고정합니다.**

- **환율**: [§3-1](#3-1-원화-환산--현재-환율-기준)이 항상 "최신 1건"을 쓰므로 **자동으로 충족됩니다.** 별도 처리 불필요.
- **지수**: 차트를 그리려면 채워야 합니다. 코스피와 S&P500은 **휴일이 서로 달라서**(추석 vs 추수감사절), 같은 날짜축에 올리면 한쪽만 구멍이 납니다.

```sql
CREATE OR REPLACE VIEW gold.v_market_index_daily AS
WITH codes AS (
  SELECT DISTINCT index_code FROM silver.market_indices
),
cal AS (
  SELECT d::date AS calendar_date
    FROM generate_series(
           (SELECT MIN(trade_date) FROM silver.market_indices),
           CURRENT_DATE,
           INTERVAL '1 day'
         ) d
)
SELECT c.index_code,
       cal.calendar_date,
       m.close_value,
       m.trade_date                            AS source_trade_date,
       (m.trade_date <> cal.calendar_date)     AS is_carried_forward
  FROM cal
 CROSS JOIN codes c
  LEFT JOIN LATERAL (
       SELECT close_value, trade_date
         FROM silver.market_indices s
        WHERE s.index_code = c.index_code
          AND s.trade_date <= cal.calendar_date
        ORDER BY s.trade_date DESC
        LIMIT 1
  ) m ON true;
```

- `is_carried_forward = true`면 "그날 장이 안 열려서 직전 값을 그대로 쓴 것"입니다. 앱이 툴팁으로 구분 표시할 수 있습니다.
- 이 뷰는 **매 조회마다 전 기간을 계산**합니다. 데이터가 수천 행 수준이라 당장은 문제없지만, 느려지면 `MATERIALIZED VIEW`로 바꾸고 배치 끝에 `REFRESH`하세요.

### 3-3. 계층 분류

silver 두 테이블은 **앱이 직접 읽지 않습니다.** 위 gold 뷰들을 통해서만 노출합니다.

> 🔴 **[미결 D-3] 이 gold 뷰를 어떤 API로 내보낼지는 이 문서의 범위 밖입니다.** 엔드포인트·응답 스키마·에러 코드·캐시 정책은 별도 API 계약 문서가 필요합니다.

### 4-2. 실패 감지와 알림

"조용히 안 쌓이는 것"이 가장 위험합니다. 아래는 **재량이 아니라 필수 요구사항**입니다.

| 조건 | 판정 | 조치 |
|---|---|---|
| `result != 1` (수출입은행) | 실패 | 즉시 알림. 특히 `3`(인증 오류)은 **키 만료 신호** |
| `resultCode != "00"` (공공데이터포털) | 실패 | 즉시 알림 |
| 영업일인데 저장 행 0건 | 실패 | 알림 (주말·공휴일은 정상) |
| 전일 대비 환율 ±5% 초과 | 경고 | 알림 후 사람이 확인 (파싱 버그 탐지용) |
| 마지막 적재일이 3영업일 이상 경과 | 실패 | 알림 |

- **응답 스키마 검증**: 외부 API 응답은 **Pydantic 모델로 파싱**합니다. 상대가 필드명을 바꾸면 파싱 단계에서 즉시 실패해야지, `None`이 조용히 흘러들면 안 됩니다.
- **인증키 보안**: 두 API 모두 **키가 URL 쿼리스트링에 들어갑니다.** 요청 URL을 로그에 남길 때 반드시 `authkey`/`serviceKey`를 **마스킹**하세요. 키는 환경변수 또는 AWS Secrets Manager에 보관합니다.

## 부록 A. 향후 계획 — JPY(엔화) 수집

**v1 범위에서 제외합니다.** 일본 카드 시세(엔화 표기) 소스를 붙이는 시점에 재개합니다.

재개 시 필요한 내용:
- `cur_unit`이 `"JPY(100)"`이고 **값도 100엔당 가격**입니다.
- `currency_code`는 `JPY`로 정규화하되, **÷100을 빠뜨리면 환율이 100배가 됩니다.**
- ⚠️ **원값 그대로 저장하고 나눗셈은 조회 시점에 하는 것을 권합니다.** bronze를 생략하는 구조라, ÷100한 값만 저장하면 **원본이 어디에도 남지 않습니다.** `unit` 컬럼(USD=1, JPY=100)을 추가하는 방식이 안전합니다.
- 이 경우 `fx_exchange_rates`에 `unit SMALLINT NOT NULL DEFAULT 1` 컬럼 추가가 필요하므로, **지금 미리 넣어둘지 검토**할 만합니다(나중에 추가하면 마이그레이션 + 기존 뷰 수정).
