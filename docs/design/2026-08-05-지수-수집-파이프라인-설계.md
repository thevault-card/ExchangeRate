## 0. 결정 요약

이 설계는 스펙 rev.2를 **좁혀서** 1차 구현 범위를 정한 것입니다. 스펙과 달라진 곳은 아래 표가 전부입니다.

| # | 결정 | 스펙 대비 |
|---|---|---|
| **A-1** | 1차 범위는 **시장지수만**. 환율 파이프라인은 보류 | 축소 |
| **A-2** | 코스피도 **yfinance `^KS11`** 로 수집. 공공데이터포털 확정 단계는 보류 | 스펙 D-1의 C안을 **1단계만 먼저** |
| **A-3** | 코스피 적재값은 `is_provisional = true` — "나중에 공식 확정값으로 덮일 예정" | 스펙 §2-4 컬럼을 그대로 채택 |
| **A-4** | **로컬 PostgreSQL** 로 먼저 만들고, TheVault 이식은 나중에 준비 | 스펙은 TheVault DB 내부를 전제 |
| **A-5** | 카드 시세와 조인하는 gold 뷰(§3-1)는 **이 저장소 밖** | 경계 명시 |

**A-2의 효과**: 코스피를 yfinance로 받으면 장 마감 직후 당일 값이 들어옵니다. 스펙 §2-3이 착수 차단으로 걸어둔 **D-1 지연 문제(익일 13시 이후 제공)가 일단 사라집니다.** 인증키도 필요 없어져, 외부 승인을 기다리지 않고 바로 착수할 수 있습니다.

## 1. 무엇을 만드나

앱 마이페이지에서 **내 자산 가치를 S&P500·코스피와 비교하는 차트**를 그리려면 두 지수의 일별 종가가 필요합니다. 이 저장소는 그 값을 매일 모아 DB에 쌓는 **배치 프로그램**입니다.

API 서버가 아닙니다. 지금은 이 데이터를 읽어 갈 서비스가 아직 없어서, HTTP 엔드포인트를 만들면 곧바로 놀게 됩니다. cron이 부르는 CLI 배치로만 만듭니다.

## 2. 범위

| 포함 | 제외 (붙일 자리만 남김) |
|---|---|
| S&P500 종가 수집 (`^GSPC`) | 환율(USD→KRW) 수집 — 스펙 §1 전체 |
| 코스피 종가 수집 (`^KS11`) | 공공데이터포털 코스피 확정값 — 스펙 §2-2 |
| `silver.market_indices` 테이블 | `silver.fx_exchange_rates` 테이블 |
| carry-forward gold 뷰 (스펙 §3-2) | 원화 환산 gold 뷰 (스펙 §3-1) |
| 실패 감지·알림 (스펙 §4-2) | 조회용 API (스펙 미결 D-3) |
| 로컬 PostgreSQL + alembic | TheVault DB로의 실제 이식 |

제외 항목은 **버리는 게 아니라 미루는 것**입니다. 각각을 나중에 붙일 때 기존 코드를 고치지 않아도 되도록 설계하는 것이 이 문서의 숨은 목표입니다. → [§10 이식 준비](#10-이식-준비)

### 3-1. 어댑터 경계

`sources/`와 `jobs/`를 나누는 것이 이 구조의 핵심입니다. 스펙 §2-1이 **"소스 교체가 쉽도록 어댑터 인터페이스 뒤에 숨긴다"** 를 설계 요구사항으로 못박았고, 우리는 그 교체가 **일어날 예정임을 이미 알고 있습니다**(→ [§8 약관 리스크](#8-알아두어야-할-리스크)).

```python
# sources/base.py
@dataclass(frozen=True)
class IndexPoint:
    index_code: str        # SPX | KOSPI
    trade_date: date       # 거래소 현지 거래일 (KST 변환 금지)
    close_value: Decimal
    source: str            # yfinance

class IndexSource(Protocol):
    def fetch(self, index_code: str, lookback_days: int) -> list[IndexPoint]:
        ...
```

`lookback_days`는 **달력 일수**입니다. yfinance 구현체에서 `period="5d"`로 넘어가고, 그 안에 거래일이 몇 개 들어 있는지는 소스가 정합니다(휴일이 끼면 5개보다 적습니다). 배치는 개수를 세지 않고 받은 만큼 적재합니다.

`jobs/`는 `IndexSource`만 알고 yfinance를 모릅니다. 나중에 유료 API나 공공데이터포털로 갈아끼울 때 **새 구현체 파일 하나만 추가**하면 됩니다.

| `index_code` | yfinance 티커 |
|---|---|
| `SPX` | `^GSPC` |
| `KOSPI` | `^KS11` |

### 3-2. 왜 `http.py`가 없나

스펙 §4-3은 타임아웃·재시도 정책을 요구하는데, 1차 범위에서는 **우리가 직접 HTTP를 부르지 않습니다.** yfinance가 내부에서 처리하죠. 그래서 범용 HTTP 래퍼 대신 **`retry.py`(호출 자체를 감싸는 재시도)** 만 둡니다.

인증키가 없으므로 스펙 §4-2의 **URL 키 마스킹 규칙도 지금은 해당 사항이 없습니다.** 환율이나 공공데이터포털을 붙이는 시점에 `http.py`와 마스킹이 함께 들어옵니다. → `docs/porting.md`

## 4. 데이터 모델

스펙 §2-4를 그대로 따릅니다.

```sql
CREATE SCHEMA IF NOT EXISTS silver;
CREATE SCHEMA IF NOT EXISTS gold;    -- §7 뷰가 들어갈 자리

CREATE TABLE silver.market_indices (
    index_code       VARCHAR(10)   NOT NULL,
    trade_date       DATE          NOT NULL,
    close_value      NUMERIC(14,2) NOT NULL,
    source           VARCHAR(30)   NOT NULL,
    is_provisional   BOOLEAN       NOT NULL DEFAULT false,
    created_at       TIMESTAMPTZ   NOT NULL DEFAULT now(),
    updated_at       TIMESTAMPTZ   NOT NULL DEFAULT now(),
    created_batch_id TEXT,
    updated_batch_id TEXT,
    CONSTRAINT pk_market_indices PRIMARY KEY (index_code, trade_date),
    CONSTRAINT ck_market_indices_close_positive CHECK (close_value > 0)
);
```

**PK 컬럼 순서 `(index_code, trade_date)` 를 뒤집지 마세요.** 실제 조회가 `WHERE index_code='KOSPI' ORDER BY trade_date DESC` 형태라 이 순서여야 인덱스를 탑니다.

### 4-1. `trade_date` — KST로 바꾸지 않습니다

각 지수의 **거래소 현지 거래일**을 그대로 씁니다. yfinance가 돌려주는 날짜가 이미 현지 거래일이므로, **변환하지 않는 것이 곧 정답**입니다. KST로 억지 변환하면 서머타임과 조기폐장에서 하루씩 어긋납니다. (스펙 §2-4)

### 4-2. `is_provisional` 의 의미

**"나중에 공식 확정값으로 덮일 예정인가"** 를 뜻합니다. 데이터가 틀렸다는 뜻이 아닙니다.

| 적재 경로 | 값 | 이유 |
|---|---|---|
| 코스피 (yfinance `^KS11`) | `true` | 공식 소스가 아님. 나중에 공공데이터포털 확정값으로 덮어쓸 예정 |
| S&P500 (yfinance `^GSPC`) | `false` | 2단계 확정 구조가 없음. 유료 API로 교체하더라도 값의 성격은 그대로 |

컬럼 하나와 값 하나로 미래를 열어둡니다. 확정 배치를 나중에 추가할 때 **기존 코드를 고칠 일이 없습니다.**

## 5. 배치

| 배치 | cron (KST) | 대상 | 조회 범위 | `is_provisional` |
|---|---|---|---|---|
| `index_spx` | `30 6 * * 2-6` | `^GSPC` | 최근 5일 | `false` |
| `index_kospi` | `40 15 * * 1-5` | `^KS11` | 최근 5일 | `true` |

- **매번 최근 5일치를 받아 UPSERT** 합니다. 배치가 하루 실패해도 다음 날 자동으로 메워져 공백이 안 생깁니다. (스펙 §2-1)
- `index_spx`의 cron이 화~토(`2-6`)인 이유: 미국 장은 KST 기준 **다음 날 새벽 6시경**에 끝납니다. 금요일 장 데이터는 토요일 새벽 배치가 가져옵니다.
- 서버 타임존이 UTC면 **KST 기준 시각으로 반드시 환산**하세요. (KST 06:30 = UTC 21:30 전날)

### 5-1. 코스피 15:40은 잠정 시각입니다

코스피 마감은 15:30인데 그 10분 뒤 yfinance가 아직 `NaN`이나 장중값을 줄 수 있습니다. **구현 후 며칠 실측해 보고 16:00로 미룰 여지를 둡니다.** 이 때문에 아래 NaN 규칙이 선택이 아니라 필수입니다.

> **`close`가 `NaN`/`None`인 행은 건너뜁니다.** 그대로 UPSERT하면 **이미 들어간 확정 종가를 덮어씁니다.** yfinance는 휴장일과 장중 미확정 구간에서 `NaN`을 반환합니다. (스펙 §2-4)

## 6. 적재 규칙 — 이 설계에서 가장 중요한 부분

배치는 **몇 번 돌려도 결과가 같아야 합니다**(멱등성). 같은 날 두 번 실행해도 PK 충돌로 죽으면 안 됩니다.

여기에 더해, 잠정값과 확정값이 섞이는 순간 **스펙에 없는 문제**가 하나 생깁니다.

> 스펙 §2-4의 UPSERT 규칙은 `값이 다르면 UPDATE` 하나뿐입니다. 이대로 두면 **잠정 배치가 어떤 이유로든 늦게 돌 때 이미 들어간 확정값을 잠정값으로 되돌립니다.** 확정값을 덮어쓰는 사고입니다.

그래서 **덮어쓰기에 방향을 강제합니다** — 잠정은 확정을 못 건드리고, 확정은 항상 이깁니다.

### 6-1. 잠정 적재 (코스피)

```sql
INSERT INTO silver.market_indices
       (index_code, trade_date, close_value, source, is_provisional,
        created_at, updated_at, created_batch_id, updated_batch_id)
VALUES (:index_code, :trade_date, :close_value, :source, true,
        now(), now(), :batch_id, :batch_id)
ON CONFLICT (index_code, trade_date) DO UPDATE
   SET close_value      = EXCLUDED.close_value,
       source           = EXCLUDED.source,
       updated_at       = now(),
       updated_batch_id = EXCLUDED.updated_batch_id
 WHERE silver.market_indices.is_provisional = true
   AND silver.market_indices.close_value IS DISTINCT FROM EXCLUDED.close_value;
```

`is_provisional = true` 조건이 **확정본을 보호하는 방어선**입니다.

### 6-2. 확정 적재 (S&P500 · 나중의 공공데이터포털)

```sql
INSERT INTO silver.market_indices
       (index_code, trade_date, close_value, source, is_provisional,
        created_at, updated_at, created_batch_id, updated_batch_id)
VALUES (:index_code, :trade_date, :close_value, :source, false,
        now(), now(), :batch_id, :batch_id)
ON CONFLICT (index_code, trade_date) DO UPDATE
   SET close_value      = EXCLUDED.close_value,
       source           = EXCLUDED.source,
       is_provisional   = false,
       updated_at       = now(),
       updated_batch_id = EXCLUDED.updated_batch_id
 WHERE silver.market_indices.is_provisional = true
    OR silver.market_indices.close_value IS DISTINCT FROM EXCLUDED.close_value;
```

잠정본이면 값이 같아도 덮어써서 `is_provisional`을 `false`로 내립니다. 확정본끼리는 값이 바뀐 경우만 갱신합니다.

### 6-3. 마지막 `WHERE` 절이 왜 필요한가

값이 그대로면 UPDATE를 건너뛰어 **`updated_at`이 매일 무의미하게 갱신되는 걸 막습니다.** 그래야 나중에 "실제로 값이 바뀐 날"을 추적할 수 있습니다. (스펙 §1-5)

## 7. gold 뷰 — carry-forward

silver에는 **실제로 발표된 값만** 저장합니다. 빈 날짜를 메우는 것은 gold 뷰에서 합니다. (silver = 사실, gold = 표현)

차트를 그리려면 휴일을 채워야 하는데, 코스피와 S&P500은 **휴일이 서로 달라서**(추석 vs 추수감사절) 같은 날짜축에 올리면 한쪽만 구멍이 납니다.

```sql
CREATE OR REPLACE VIEW gold.v_market_index_daily AS
WITH codes AS (
  SELECT DISTINCT index_code FROM silver.market_indices
),
cal AS (
  SELECT d::date AS calendar_date
    FROM generate_series(
           (SELECT MIN(trade_date) FROM silver.market_indices),
           CURRENT_DATE,
           INTERVAL '1 day'
         ) d
)
SELECT c.index_code,
       cal.calendar_date,
       m.close_value,
       m.trade_date                        AS source_trade_date,
       m.is_provisional,
       (m.trade_date <> cal.calendar_date) AS is_carried_forward
  FROM cal
 CROSS JOIN codes c
  LEFT JOIN LATERAL (
       SELECT close_value, trade_date, is_provisional
         FROM silver.market_indices s
        WHERE s.index_code = c.index_code
          AND s.trade_date <= cal.calendar_date
        ORDER BY s.trade_date DESC
        LIMIT 1
  ) m ON true;
```

- `is_carried_forward = true` 면 "그날 장이 안 열려서 직전 값을 그대로 쓴 것"입니다. 앱이 툴팁으로 구분할 수 있습니다.
- `is_provisional`도 함께 내보냅니다 — 앱이 "잠정치" 표기를 할 수 있어야 합니다.
- 이 뷰는 매 조회마다 전 기간을 계산합니다. 데이터가 수천 행 수준이라 당장은 괜찮지만, 느려지면 `MATERIALIZED VIEW`로 바꾸고 배치 끝에 `REFRESH` 하세요.

**silver 테이블은 앱이 직접 읽지 않습니다.** 이 뷰를 통해서만 노출합니다.

## 9. 운영

### 9-1. 실패 감지 — 재량이 아니라 필수

**"조용히 안 쌓이는 것"이 가장 위험합니다.** (스펙 §4-2)

**2026-08-07 개정**: 영업일 판정을 **요일 기반에서 거래소 캘린더 기반**으로 바꿨습니다.
요일만 보면 두 가지가 깨집니다 — 평일 공휴일에 "영업일인데 0건"으로 거짓 실패가
나고, `index_spx`(cron `30 6 * * 2-6`)의 **토요일 06:30 KST 실행**(미국 금요일
종가를 받는 그 주 마지막 수집)은 `is_business_day(토)==False`라 0건이어도 "휴장"
으로 조용히 넘어갑니다. 이제는 "오늘이 영업일인가"가 아니라 **"이 거래소의
가장 최근 마감 세션까지 우리가 갖고 있는가"**를 묻습니다(`exchange_calendars`
패키지, `alerts.is_session` / `alerts.last_due_session` / `alerts.check_freshness`).
요일·공휴일·토요일 실행이 전부 이 한 규칙으로 처리됩니다.

| 조건 | 판정 | 조치 |
|---|---|---|
| 마감 + 유예(`AVAILABILITY_GRACE`)가 지난 세션의 데이터가 없음 | 실패 | `check_freshness` → `BatchFailure` → 알림 + 종료코드 1 |
| `close`가 `NaN`/`None` | 경고 | 그 행만 건너뛰고 계속 |
| 전일 대비 ±10% 초과 | 경고 | 사람이 확인 (파싱 버그 탐지용) |
| 마지막 적재일 이후 마감된 세션이 3개 이상 | 실패 | `check_staleness` → `BatchFailure` (세션 수로 센다. 요일이 아니다) |

- 스펙 §4-2의 환율 기준은 ±5%지만, **지수는 변동성이 더 커서 ±10%로 둡니다.** 서킷브레이커가 걸려도 하루 10%를 넘기는 일은 드뭅니다.
- **응답 스키마 검증**: 외부 데이터는 `IndexPoint`로 변환하는 지점에서 검증합니다. 상대가 형태를 바꾸면 그 자리에서 즉시 실패해야지, `None`이 조용히 흘러들면 안 됩니다.
- **`AVAILABILITY_GRACE`**: 세션 마감 후 소스에 데이터가 뜨기까지 주는 유예(현재 시장별 30분, `config.py`). 코스피 15:40 배치는 마감(15:30) 직후라 유예가 없으면 매번 거짓 실패합니다. **잠정값이며 §13 B-3의 실측 후 조정 대상**입니다.
- **3상태**: 배치는 `success` / `market_closed`(0건이지만 알림 대상 아님, 종료코드 0) / `failure`(종료코드 1) 중 하나로 끝나고, 로그의 `status` 필드에 남습니다 (`jobs.JobStatus`).

### 9-2. 알림 채널

1차 범위에서는 **stdout JSON 로그 + 실패 시 종료코드 1** 입니다. 판정 로직은 지금 전부 구현하고, 나중에 채널만 CloudWatch나 Slack으로 바꿉니다.

### 9-3. 외부 호출 정책

| 항목 | 값 |
|---|---|
| 재시도 | 3회, 지수 백오프 (2s → 4s → 8s) |
| 재시도 대상 | 타임아웃, 네트워크 오류, 빈 응답 |
| 재시도 제외 | 없음 (yfinance는 인증·한도 개념이 없음) |

yfinance 호출을 `retry.py` 래퍼로 감쌉니다. 타임아웃은 yfinance 내부 값을 따릅니다.

### 9-4. 배치 식별자

모든 적재는 `batch_id`를 남깁니다. 형식은 `{job명}-{실행시각ISO}` (예: `index_kospi-2026-08-05T15:40:00+09:00`). 어느 실행이 어느 행을 만들었는지 추적하기 위한 것입니다.

## 10. 이식 준비

**"로컬에서 먼저 만들고 나중에 TheVault로 옮긴다"** 가 A-4 결정입니다. 옮길 때 고생하지 않도록 지금부터 지키는 규칙이 넷입니다.

| # | 규칙 | 이유 |
|---|---|---|
| P-1 | 스키마명을 `silver.*` / `gold.*` 로 유지 | TheVault 정의서와 이름이 이미 같으면 옮길 때 바꿀 게 없음 |
| P-2 | alembic 리비전을 독립적으로 (`down_revision = None`) | TheVault 마이그레이션 체인 뒤에 이어붙일 수 있어야 함 |
| P-3 | DB 접속은 `DATABASE_URL` 환경변수 하나로만 | 접속 대상 교체가 설정 한 줄 |
| P-4 | 거버넌스 컬럼 4종 패턴 유지 | 기존 `ppt_*` 테이블과 같은 형태 |

`docs/porting.md`에 아래를 보관합니다.

1. **스펙 §3-1 원화 환산 뷰 SQL** — 카드 시세 테이블(`silver.fact_card_price`)이 있는 쪽에 붙는 순간 그대로 실행됩니다. 이 저장소에는 그 테이블이 없어 만들 수 없습니다.
2. **환율 파이프라인 추가 시 할 일** — 수출입은행 어댑터, `fx_exchange_rates` 테이블, `http.py`와 키 마스킹, 스펙 §1-2의 함정 3개(콤마 파싱 / `result != 1` / USD 필터).
3. **공공데이터포털 코스피 확정 배치 추가 시 할 일** — 어댑터 하나 + [§6-2 확정 적재](#6-2-확정-적재-sp500--나중의-공공데이터포털) SQL 재사용. 스펙 §2-2의 함정 3개(serviceKey 이중 인코딩 / 한글 파라미터 / 에러도 HTTP 200)와 **필드명 실호출 미검증** 숙제.
4. **미결 D-6 쟁점** — 기존 TheVault silver는 `dim_*`/`fact_*` + 대리키 `*_sk` + naive `timestamp`인데 이 설계는 **자연키 PK + `TIMESTAMPTZ`** 입니다. 예외로 둘지 통일할지는 이식 시점에 결정합니다.

## 11. 테스트

**외부 API를 실제로 부르지 않습니다.** yfinance 응답을 DataFrame 픽스처로 고정하고 `yf.download`를 대체합니다. 그래야 테스트가 네트워크와 장 시간에 좌우되지 않습니다.

스펙이 경고한 함정들이 곧 테스트 목록입니다.

| 대상 | 확인할 것 |
|---|---|
| 소스 어댑터 | 정상 응답 → `IndexPoint` 변환 · **`NaN` 행 건너뛰기** · 빈 응답 → 실패 · 티커 매핑 |
| `trade_date` | 현지 거래일이 KST로 변환되지 **않는지** |
| 적재 | 같은 배치 2회 실행 → `updated_at` 불변 (멱등성) |
| 적재 | **잠정이 확정을 덮지 못하는지** ← 가장 중요 |
| 적재 | 확정이 잠정을 덮고 `is_provisional`이 `false`로 내려가는지 |
| gold 뷰 | 휴일 날짜에 직전값 + `is_carried_forward = true` |
| gold 뷰 | 코스피·S&P500 휴일이 어긋나도 양쪽 다 채워지는지 |
| 실패 감지 | 판정 5종이 각각 발동하는지 |

DB 테스트는 로컬 PostgreSQL(docker-compose)에 붙여 실행하고, 각 테스트를 트랜잭션 롤백으로 격리합니다.

## 12. 완료 기준

구현이 끝났다고 말하려면 아래가 전부 실제로 통과해야 합니다.

1. `docker compose up -d` 후 `alembic upgrade head` → `silver.market_indices` 와 `gold.v_market_index_daily` 생성
2. `python -m collector index_spx` → 최근 5거래일 행 적재, `is_provisional = false`
3. `python -m collector index_kospi` → 행 적재, `is_provisional = true`
4. 같은 명령을 한 번 더 실행 → 행 수·`updated_at` 모두 불변 (멱등성)
5. `gold.v_market_index_daily` 조회 → 주말 날짜에 직전 거래일 값 + `is_carried_forward = true`
6. 테스트 전부 통과 · ruff 통과
