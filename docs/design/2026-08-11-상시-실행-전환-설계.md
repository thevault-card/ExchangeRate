# 상시 실행 전환 설계 (12시간 주기)

> 2026-08-11 · 대상: 이 저장소의 수집기를 개인 PC 작업 스케줄러에서 **상시 켜진 환경(AWS)** 으로 옮기고, 실행 주기를 **12시간**으로 단순화한다.
> 선행 문서: [2026-08-05 지수 수집 파이프라인 설계](2026-08-05-지수-수집-파이프라인-설계.md) — 적재 규칙·판정 규칙은 그 문서가 정본이고, 여기서는 **언제·어디서 도는가**만 다룬다.

---

## 1. 왜 옮기는가

지금 자동화는 Windows 작업 스케줄러 5개 작업 + `scripts/run_job.cmd` 로 이미 돌고 있고, 8/7 이후 매일 성공하고 있다. 유일한 결함은 **PC 가 꺼져 있으면 안 돈다**는 것이다.

실측 증거: 8/11 의 `fx-am`(11:10 예정) 이 12:04 에, `index-kospi`(16:30 예정) 가 17:17 에 실행됐다. 작업 스케줄러의 "놓친 실행 보상" 이 메워준 것이고, 보상이 없거나 하루를 통째로 꺼두면 그날은 공백이다.

> 공백 자체는 치명적이지 않다. 배치가 **매번 최근 5일치를 UPSERT** 하므로 하루 빠져도 다음 실행이 메운다(설계 §5). 그래서 이 전환은 "데이터 유실 방지"가 아니라 **"사람 손이 안 가게 하는 것"** 이 목적이다. 이 구분이 뒤의 결정 대부분을 정한다 — 비싸고 정교한 인프라를 쓸 이유가 없다.

## 2. 어디서 도는가

| 안 | 새로 배우는 것 | 비용(월) | 판단 |
|---|---|---|---|
| **EC2 t4g.nano + cron** | EC2·cron 뿐 | ~$3 (프리티어면 $0) | **채택** |
| ECS Fargate + EventBridge Scheduler | Dockerfile·ECR·태스크 정의·EventBridge | ~$1 | 개념 4개 추가. 나중에 백엔드가 ECS 로 가면 그때 합류시켜도 늦지 않음 |
| Lambda + EventBridge | 레이어 패키징·15분 제한 | ~$0 | `yfinance`·`exchange_calendars`·`psycopg` 패키징이 무겁고, `fx_backfill` 이 15분을 넘김 |

**EC2 t4g.nano 1대 + cron.** 이 저장소는 `uv` 로 실행되고 의존성이 파이썬 하나뿐이라 컨테이너로 감쌀 이유가 없다. 배포는 `git pull` + `uv sync` 두 줄이다.

- OS: Amazon Linux 2023 (arm64)
- 타임존: **인스턴스는 UTC 로 두고 cron 에 KST 를 환산해 쓰지 않는다.** 대신 `TZ=Asia/Seoul` 을 crontab 상단에 선언한다. 시각 환산 실수는 이 파이프라인에서 가장 흔한 사고 유형이다(설계 §5).
- 로그: 지금처럼 stdout JSON 한 줄. CloudWatch Agent 를 붙이면 그대로 흘러 들어간다(별도 포맷 변경 불필요).
- 비밀값: `.env` 파일을 인스턴스에 두고 `uv run --env-file .env` 유지. SSM Parameter Store 는 키가 늘어나면 그때 옮긴다.

## 3. 언제 도는가 — 12시간 주기

배치별로 다른 시각을 잡던 것을 **하루 2회, 12시간 간격**으로 통일한다.

```cron
TZ=Asia/Seoul
30 6  * * * /home/ec2-user/ExchangeRate/scripts/run_all.sh
30 18 * * * /home/ec2-user/ExchangeRate/scripts/run_all.sh
```

> **2026-08-13: 이 주기를 로컬 작업 스케줄러에 먼저 적용했다.** 배치별 작업 4개(06:30·11:10·16:10·16:30)를 `ExchangeRate-collect` 하나로 합치고 트리거를 06:30·18:30 두 개로 뒀다. 옛 작업 4개는 삭제하지 않고 **사용 안 함**으로 남겨뒀다. EC2 이전은 이 구조를 셸로 옮기는 일만 남는다.

| 실행 | 이 실행이 노리는 데이터 | 나머지 배치는 |
|---|---|---|
| **06:30 KST** | `index_spx` — 미국 장 마감(≈06:00 KST) 직후 | `index_kospi`·`fx_daily` 는 전날 것을 이미 갖고 있어 **스킵** |
| **18:30 KST** | `index_kospi`(15:30 마감), `fx_daily`(수출입은행 11시경 고시) | `index_spx` 는 아침에 받아둬 **스킵** |

`run_all.sh` 는 세 배치를 순서대로 부르고, 각 배치가 스스로 "지금 나는 돌 필요가 있는가"를 판단한다(§4). 즉 **스케줄이 배치를 고르지 않는다** — 시각표를 관리할 일이 없어진다.

> 요일 조건(`* * 1-5`, `2-6`)도 전부 뺐다. 주말 판정은 cron 이 아니라 거래소 캘린더가 한다(§4-2). cron 에 요일을 적으면 공휴일은 여전히 못 거르므로 판정이 두 곳에 흩어질 뿐이다.

**바뀌는 것:** KOSPI 종가가 DB 에 들어오는 시각이 16:30 → 18:30 으로 2시간 늦어진다. 현재 이 데이터를 읽어 가는 서비스가 없으므로(설계 §2) 무해하다. 실시간성이 필요해지면 그때 KOSPI 만 별도 cron 으로 떼어낸다.

## 4. 예외 처리 — 두 경우가 사실 하나다

12시간 주기로 돌리면 **모든 실행의 절반 이상이 "할 일 없음"** 이다. 이걸 실패로 보지 않는 것, 그리고 **할 일이 없으면 외부 API 를 호출하지도 않는 것**이 이 설계의 본체다.

### 4-1. 판정 규칙 (신규)

```python
# jobs.py — fetch 이전에 부른다
def _up_to_date(market: str, latest_stored: date | None, now: datetime) -> bool:
    """이번 실행에서 새로 받을 게 있는가. 없으면 True."""
    due = alerts.last_due_session(market, now)
    return due is not None and latest_stored is not None and latest_stored >= due
```

`last_due_session()` 은 [alerts.py:40](../../src/collector/alerts.py#L40) 에 **이미 있다.** "마감 + 유예가 지난 세션 중 가장 최근 것"을 돌려주므로,

- **이미 적재된 경우** → `latest_stored >= due` → 스킵
- **주말·공휴일** → `due` 가 직전 영업일(금요일 등)을 가리키고 그건 이미 갖고 있음 → 같은 조건으로 스킵
- **아직 아무 세션도 안 지남**(`due is None`, 예: 개장 전 첫 실행) → 스킵

세 경우가 한 조건으로 처리된다. 요일 검사도, "오늘 휴장인가" 조회도 따로 두지 않는다.

### 4-2. 실행 흐름

```
run_index / run_fx
  │
  ├─ latest = db.latest_date(...)              ← DB 조회 1회 (API 호출 없음)
  │
  ├─ _up_to_date(...) 이면
  │     └─ log{status: "up_to_date", latest} → 종료코드 0 ── 여기서 끝. fetch 안 함
  │
  ├─ fetch (yfinance / 수출입은행)
  ├─ upsert  (값이 같으면 UPDATE 스킵 — 기존 멱등 규칙 그대로)
  └─ check_freshness → 미달이면 BatchFailure → 종료코드 1
```

**fetch 를 건너뛰는 것이 핵심 이득이다.** 수출입은행 API 는 일일 호출 한도가 있고(`RateLimitError` 처리가 이미 있다), 12시간 주기면 하루 2회 중 1회는 확실히 불필요한 호출이 된다.

### 4-3. 상태값

기존 `JobStatus` 에 하나만 추가한다.

| status | 의미 | 종료코드 | 알림 |
|---|---|---|---|
| `up_to_date` | **(신규)** 최신 세션까지 이미 적재됨 — 주말·휴장·중복 실행 모두 여기 | 0 | 없음 |
| `success` | 새로 받아 적재함 | 0 | 없음 |
| `market_closed` | 받았는데 0건 (사후 판정, 남겨둠) | 0 | 없음 |
| `skipped` | `FX_ENABLED=false` | 0 | 없음 |
| `rate_limited` | 일일 한도 — 다음 실행이 이어받음 | 0 | 없음 |
| `failure` | 마감 세션 미달 / 소스 오류 | 1 | **대상** |

> `market_closed` 를 지우지 않는 이유: `_up_to_date` 가 False 인데(= 받아야 하는데) 소스가 0건을 준 상황은 여전히 구분해서 봐야 한다. 캘린더가 틀린 경우가 그렇게 드러난다(`EXTRA_CLOSURES` 가 그렇게 발견됐다).

### 4-4. 실패 알림 (12시간 주기에 맞춘 임계)

12시간 주기에서는 **1회 실패가 곧 사고가 아니다** — 12시간 뒤 실행이 최근 5일치를 다시 받아 저절로 메운다. 그래서 알림은 **연속 2회 실패**부터 보낸다. 판정 상태는 파일 하나면 충분하다.

```
logs/consecutive_failures      # 성공하면 0 으로 덮어쓰기, 실패하면 +1
                               # 2 이상이 되는 순간에만 알림
```

채널은 미정(§6). 그 전까지는 종료코드 1 + 로그로 둔다 — 지금과 같다.

## 4-5. 적재 대상 — vaultdb 직접 (2026-08-12 **전환 완료**)

로컬 PG 에 쌓고 `upload_to_thevault.py` 로 수동 업로드하던 2단계를 없앴다. `DATABASE_URL` 이 vaultdb 를 직접 가리킨다.

> **EC2 이전보다 먼저 했다.** 원래는 "인바운드 열린 뒤"로 순서를 잡았는데, 인바운드는 **EC2 에서** 붙기 위한 것이고 개발 PC 는 이미 vaultdb 에 붙는다. 둘을 분리해 전환을 먼저 끝냈고, EC2 이전은 인바운드가 열리면 그때 한다.

| | 이전 | 지금 |
|---|---|---|
| 수집기가 쓰는 곳 | 로컬 PG `silver.*_test` | **vaultdb `silver.fx_exchange_rates` · `silver.market_indices`** |
| vaultdb 반영 | 사람이 스크립트로 수동 | 로컬 스케줄러가 직접 (하루 4회, EC2 이전 후 2회) |
| `batch_id` | `vaultuser` | 그대로 — 접속 계정이 곧 vaultuser 라 코드 변경 없음 |

### 테이블 이름을 로컬까지 통일했다

`config.py` 의 `_test` 접미사를 떼면서, **로컬 `exchangerate_dev` 의 테이블도 같은 이름으로 RENAME** 했다. 이제 어느 DB 를 향하는지는 `DATABASE_URL` 하나로만 갈린다(설계 §10 P-3). 이름이 같아진 대가로 "테이블 이름이 다르니 실수해도 안전하다"는 방어가 사라졌고, 그 자리를 아래 1번이 대신한다.

### 지켜야 할 선 넷

1. **테스트는 절대 vaultdb 로 돌리지 않는다.** [conftest.py](../../tests/conftest.py) 는 `DATABASE_URL` 로 **실제 DB 에 접속해** 쓰고 롤백한다. `test_jobs.py` 는 `FUTURE = 2099-01-01` 같은 행을 실제로 INSERT 한다 — 커밋 실수 한 번이면 그대로 남는다.
   → **`conftest.py` 가 `DATABASE_URL` 에 `rds.amazonaws.com` 이 있으면 `pytest` 자체를 거부한다.** 테스트는 반드시 로컬 DSN 을 담은 `.env.local` 로 돌린다: `uv run --env-file .env.local pytest`
2. **로컬 PC 작업 스케줄러와 EC2 가 동시에 돌지 않게 한다.** 지금은 로컬 스케줄러만 vaultdb 에 쓴다. EC2 로 옮기는 순간 로컬 작업 5개를 **사용 안 함** 으로 바꾼다(M-6). 둘 다 돌면 같은 행을 두 곳에서 쓴다.
3. **UPSERT 는 `DO UPDATE` 를 유지한다.** 수동 업로드 스크립트는 `DO NOTHING` 이었지만(남의 데이터를 조용히 바꾸지 않으려는 방어), 이제 이 두 테이블은 이 파이프라인이 단독으로 채운다. 잠정 KOSPI 종가를 확정값으로 교체하려면 갱신이 가능해야 한다. 값이 같으면 UPDATE 를 건너뛰는 멱등 규칙과, 잠정이 확정을 못 건드리는 방향 규칙이 방어를 맡는다.
4. ~~`make_upload_sql.py` · `upload_to_thevault.py` 폐기~~ → **2026-08-13 삭제 완료.** 존재 이유(수동 2단계)가 사라졌다.

### 전환 실적 (2026-08-12)

vaultdb 는 8/8 수동 업로드분(8/6~8/7)까지만 있었고, 전환 첫 실행이 밀린 3일치를 채웠다.

| 대상 | 전환 전 | 전환 후 | 최신일 |
|---|---|---|---|
| SPX | 752행 (8/6) | **756행** | 8/12 |
| KOSPI | 729행 (8/7) | **732행** | 8/12 |
| FX USD·JPY | 각 733행 (8/7) | **각 736행** | 8/12 |

환율도 자동으로 메워졌다 — `run_fx` 가 당일 1건만 받던 결함을 M-1 에서 같이 고쳐, `fx_backfill` 수동 실행(구 M-9)이 필요 없어졌다.

### 전환으로 **잃은 것** — DB 방어선 (미해결, 요청 중)

로컬 `exchangerate_dev` 는 `schema.sql` 로 제약을 걸어뒀지만, **vaultdb 의 대상 테이블에는 PK 말고 아무것도 없다.**

| | 로컬 `exchangerate_dev` | vaultdb (대상) |
|---|---|---|
| PK | ✅ | ✅ |
| `CHECK (> 0 AND < Infinity)` | ✅ `ck_market_close_positive` · `ck_fx_base_rate_positive` | ❌ 없음 |
| `source`·`created_at`·`updated_at` NOT NULL | ✅ | ❌ 전부 nullable |
| `gold.v_market_index_daily` (carry-forward 뷰, 설계 §7) | ✅ | ❌ 없음 (gold 스키마엔 다른 객체 18개가 있음) |

파싱 버그로 0·NULL 이 들어가는 것을 로컬에서는 DB 가 막아준다. vaultdb 에는 그 그물이 없고, **UPSERT 라 이미 들어가 있던 정상값을 덮어쓴다.**

코드 쪽 방어는 넣었다 — [sources.py `_checked()`](../../src/collector/sources.py) 가 0·음수·Infinity·NaN 을 만나면 배치를 세운다(P1, 2026-08-12). **다만 코드는 이 파이프라인만 막고, DB 제약은 모든 경로를 막는다.** 그래서 요청은 유효하다.

→ **요청 사항(성호님·준서님):** 아래 DDL 그대로. 위반 행 0건·1,472/1,488행이라 즉시 적용된다(2026-08-13 확인).

```sql
ALTER TABLE silver.fx_exchange_rates
  ALTER COLUMN source SET NOT NULL,
  ALTER COLUMN created_at SET NOT NULL,
  ALTER COLUMN updated_at SET NOT NULL,
  ADD CONSTRAINT ck_fx_base_rate_positive
      CHECK (base_rate > 0 AND base_rate < 'Infinity'::numeric);

ALTER TABLE silver.market_indices
  ALTER COLUMN source SET NOT NULL,
  ALTER COLUMN created_at SET NOT NULL,
  ALTER COLUMN updated_at SET NOT NULL,
  ADD CONSTRAINT ck_market_close_positive
      CHECK (close_value > 0 AND close_value < 'Infinity'::numeric);
```

carry-forward 뷰는 지금 읽어 가는 소비자가 없어 급하지 않다. 필요해지는 시점에 vaultdb 에도 만든다.

> **선행 조건이었던 성호님 합의는 2026-08-11 받았다.** 대상 테이블 2개·쓰기 주기·batch_id 값을 공유하고 동의를 얻은 뒤 전환했다.

남은 것은 전부 EC2 이전(M-3·M-5·M-6)과 문서 정리(M-4)이고, **인바운드 5432 개방이 유일한 선행 조건**이다.

### M-1 이후: 밀린 만큼 구간이 넓어진다 (2026-08-13)

`_pending_*_dates` 의 검사 시작일을 고정 창이 아니라 `min(due − lookback_days, 최신일 + 1일)` 로 잡는다.

고정 5일 창만 쓰면 그보다 오래 멈췄을 때 **최근 며칠만 채우고 최신일이 `due` 에 닿아 신선도 검사를 통과한다** — 나머지 공백이 성공으로 포장된 채 남는다. 창을 좁히지는 않아(`min`) 최신일보다 앞에 숨은 구멍도 계속 잡는다. 환율은 가장 뒤처진 통화를 기준으로 잡아 그 통화도 함께 복구된다.

상한은 두지 않는다. 지수는 yfinance 가 기간을 한 번에 주고, 환율은 일일 한도에 걸리면 `rate_limited` 로 끊고 다음 실행이 이어받는다.

### M-1 에 딸린 것: `run_fx` 는 자가 복구가 안 된다

`run_index` 는 매번 최근 5일치를 UPSERT 해서 하루 걸러도 다음 실행이 메운다. 반면 `run_fx` 는 **`fetch_fx(today)` 로 당일 1건만** 받는다. 실행이 하루 빠지면 그 날짜는 사람이 `fx_backfill` 을 수동 실행해야만 채워진다 — 2026-08-11 실측에서 vaultdb 의 fx 만 자동으로 안 메워지는 것으로 드러난 결함이 이것이다.

빠진 날짜만 골라 채우는 로직은 `run_fx_backfill` 안에 이미 있다(`_existing_fx_pairs` + `pending`). `_up_to_date` 를 넣을 때 `run_fx` 의 수집 범위를 "최근 N일 중 없는 (통화, 날짜)" 로 바꾸면, 결함 수정과 §4 스킵 판정이 한 번에 정리되고 두 함수의 중복도 줄어든다. **`fx_backfill` 에는 없는 이상치·신선도 검사가 `run_fx` 에만 있으므로, 합칠 때 그 둘을 잃지 않는 것이 유일한 주의점이다.**

정상 상황에서는 이미 있는 날짜를 건너뛰어 API 호출이 지금과 같이 1회다. 공백이 있을 때만 늘어나는데, 그게 이 수정이 노리는 동작이다.

**검증:** `_up_to_date` 는 순수 함수라 DB 없이 테스트한다 — (a) 최신 적재 = due → True, (b) 적재가 due 보다 과거 → False, (c) 토요일 실행 + 금요일치 보유 → True, (d) `due is None` → True. 실제 스킵 경로는 기존 `job_conn` 픽스처로 "fetch 가 호출되지 않았는지"를 확인한다.

## 부록. 이 설계가 **하지 않는** 것

- **컨테이너화** — 파이썬 프로세스 하나를 하루 두 번 도는 데 이미지 빌드 파이프라인을 붙이지 않는다. 백엔드가 ECS 로 확정되고 이 수집기도 거기 얹기로 하면 그때 한다.
- **작업 큐·워커** — 배치 3개가 순차로 몇 초 도는 일이다.
- **DB 안의 실행 이력 테이블** — TheVault 본 파이프라인의 `bronze.ppt_pipeline_runs` 에 해당하는 것. 여기서는 stdout JSON 로그(`ts`·`job`·`status`)가 그 역할을 한다. 로그를 질의해야 할 만큼 실행이 늘어나면 그때 만든다.
- **다중 리전·이중화** — 하루 빠져도 다음 실행이 5일치를 메운다.
